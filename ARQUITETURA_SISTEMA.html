1. Visão geral

O HappySite é um sistema web interno que administra o ciclo de trabalho de uma construtora: cadastro de obras, apontamento do que cada colaborador executou, cálculo do que cada um tem a receber, controle de EPI, ASO, agenda de compromissos e o financeiro de entrada.

O conceito central: a "célula"

Quase tudo no sistema gira em torno de uma ideia só. Uma obra é desenhada como um prédio virtual, e esse prédio é fatiado em células — cada célula é um pedaço mensurável da obra:

Cobertura
  Caixa d'água / Ático
7º Andar  →  Corredor | Elevador | Escada | Apto 701 | Apto 702 ...
6º Andar  →  Corredor | Elevador | Escada | Apto 601 | Apto 602 ...
...
Térreo    →  Corredor | Elevador | Escada | Vaga 1 | Vaga 2 ...
Laje Piso Térreo
Fundação - Etapa 1..N

Cada célula tem uma chave textual (apto-b0-a3-2, escada-terreo, fundacao-1) que é o identificador usado no banco inteiro. Marcar uma célula significa dizer: "fulano executou este serviço neste pedaço da obra, neste mês". Dessa marcação nasce todo o resto — a medição, o valor a pagar, os relatórios.

Fluxo macro

Cadastra obra (wizard: blocos, andares, aptos)
        ↓
Configura serviços da obra (alvenaria, reboco...) com preço unitário e equipe
        ↓
Marca células no desenho do prédio  ──→  grava em obra_servico_celulas (qtd + valor)
        ↓
Lança diárias e pagamentos antecipados (vale, FGTS, adiantamento...)
        ↓
Medição do mês = soma das células + diárias − descontos
        ↓
Fecha/paga a medição  →  status PAGO congela o histórico

Três decisões que explicam muita coisa

1. Camada de compatibilidade SQL (server/db/database.js) O sistema nasceu em SQLite (better-sqlite3) e migrou para PostgreSQL. Para não reescrever centenas de queries, existe um adaptador que traduz na hora:

  • placeholders ? → $1, $2, $3...
  • INSERT sem RETURNING ganha RETURNING id automaticamente (emula lastInsertRowid)
  • expõe a API antiga: db.get(), db.all(), db.run(), db.transaction()

Por isso o código das rotas usa ? mesmo sendo Postgres. É intencional.

2. Backend serve o frontend Não há servidor web separado para o React. O Express entrega a API em /api/* e também os arquivos estáticos de client/dist. Um único container, um único processo.

3. Migrações no boot Não há Prisma, Knex ou ferramenta de migration. O arquivo database.js roda um migrate() idempotente toda vez que o servidor sobe: cria tabelas com CREATE TABLE IF NOT EXISTS, adiciona colunas se não existirem, popula dados-semente. O servidor só aceita conexões depois que a promessa db.pronto resolve.

Histórico: por que um VPS

A versão anterior usava Render (free) + Neon (free). Ambos hibernavam por inatividade, causando cold start: tela branca e espera longa no primeiro acesso do dia. A migração para um VPS único — com banco, aplicação e proxy no mesmo servidor — resolveu isso. Sobraram no código alguns vestígios dessa época (rota /ping de keep-alive, comentários sobre Render, render.yaml).

4. Deploy automático

.github/workflows/deploy.yml — dispara a cada push na main (ou manualmente em Actions → Run workflow). Leva de 5 a 10 minutos.

push na main
   ↓
GitHub Actions (appleboy/ssh-action) conecta por SSH
   ↓
cd /opt/happysite
git fetch origin main && git reset --hard origin/main
   ↓
sudo docker image prune -f          ← libera RAM/disco ANTES do build
   ↓
sudo docker compose up -d --build   ← rebuild e restart
   ↓
sleep 15 && docker compose ps       ← confirma que subiu

Secrets necessários: DEPLOY_KEY (chave SSH privada), DEPLOY_HOST, DEPLOY_USER.

Detalhes que importam

  • git reset --hard, não git pull. Pull falha silenciosamente se houver qualquer alteração

local no servidor. O reset garante paridade exata com o GitHub. Arquivos no .gitignore (como o .env) não são afetados.

  • image prune antes do build. Com 2 GB de RAM, build + containers já travaram o servidor

por falta de memória.

  • concurrency: deploy-producao impede dois deploys simultâneos corrompendo o build.
  • command_timeout: 20m — o build leva de 3 a 6 minutos nesta instância.

⚠️ "Success" no GitHub ≠ aplicação no ar

O workflow pode concluir com sucesso e a aplicação estar quebrada (erro de runtime, container em loop de restart). Sempre confirme de verdade:

# 1. O workflow terminou?
Invoke-RestMethod 'https://api.github.com/repos/happySiteCerqueira/happysite/actions/runs?per_page=1'

# 2. O commit certo está no servidor e os containers de pé?
ssh -i ~/.ssh/deploy_happysite ubuntu@3.228.110.68 `
  "cd /opt/happysite && git rev-parse --short HEAD && sudo docker compose ps"

# 3. O site responde?
Invoke-WebRequest 'https://app.cerqueiraengenharia.com.br' -UseBasicParsing

Verificação pré-push

O build acontece no servidor. Um erro de sintaxe JSX derruba o deploy — já aconteceu. Se houver Node na máquina local, rode npm --prefix client run build antes do push. Sem Node, a checagem mínima é contar delimitadores:

$t = Get-Content 'client\src\pages\ObraDetalhe.jsx' -Raw
foreach ($p in @(@('{','}'),@('(',')'),@('[',']'))) {
  $a=([regex]::Matches($t,[regex]::Escape($p[0]))).Count
  $b=([regex]::Matches($t,[regex]::Escape($p[1]))).Count
  "$($p[0]) $a vs $($p[1]) $b -> $(if($a -eq $b){'OK'}else{'DESBALANCEADO'})"
}

Isso detecta desbalanceamento, mas não erros semânticos. É um paliativo, não uma garantia.

6. Backend: anatomia

Sequência de inicialização (server/server.js)

1. require('./db/database')      → dispara as migrações (promessa db.pronto)
2. verificarRotasRegistradas()   → se faltar app.use, process.exit(1)
3. Middlewares: cors, express.json (limite 10 MB)
4. GET /ping                     → keep-alive (sem auth, sem banco)
5. /comprovantes                 → arquivos enviados (estáticos)
6. app.use('/api/...')           → 17 routers
7. Estáticos do client/dist + fallback do SPA
8. await db.pronto → app.listen(3001)
9. iniciarBackupAutomatico() e iniciarAgendadorLembretes()

O passo 8 é importante: o servidor não aceita requisições antes das migrações terminarem. Se a migração falhar, o processo sai com código 1 e o container reinicia.

A trava de rotas (verificarRotas.js)

Já aconteceu de um módulo inteiro (EPI) existir em routes/ e sumir do site porque faltava o app.use() correspondente. Agora, se houver um arquivo em server/routes/ sem registro no server.js, o servidor recusa subir. Falha de propósito, para não publicar versão quebrada.

Consequência prática: ao criar server/routes/novo.js, registre-o obrigatoriamente:

app.use('/api/novo', require('./routes/novo'));

Cache e o fallback do SPA

Dois problemas reais resolvidos aqui:

1. App preso em versão antiga. Arquivos com hash no nome (index-AbC123.js) podem ser cacheados indefinidamente. Mas index.html, sw-push.js, sw.js, manifest.webmanifest e registerSW.js recebem Cache-Control: no-cache, no-store, must-revalidate — sem isso, o app instalado no celular nunca percebia que havia versão nova.

2. Tela branca após deploy. O fallback do SPA só devolve index.html para rotas de navegação (sem extensão no último segmento). Pedidos a arquivos estáticos inexistentes recebem 404 de verdade. Antes, um bundle antigo recebia o HTML com status 200, o navegador tentava executar HTML como JavaScript, falhava em silêncio e o React nunca montava.

app.get(/^(?!\/api).*/, (req, res, next) => {
  const ultimoSegmento = req.path.split('/').pop() || '';
  if (ultimoSegmento.includes('.')) return next();  // 404 real
  res.setHeader('Cache-Control', 'no-cache, no-store, must-revalidate');
  res.sendFile(path.join(clientBuildPath, 'index.html'));
});

Padrão de um arquivo de rota

const express = require('express');

  const linhas = await db.all('SELECT * FROM financeiro_receitas WHERE id = ?', id);

Observe: placeholders ? (traduzidos pelo adaptador) e parâmetros soltos, não em array.

obra_servico_celulas — ★ o coração do sistema

Cada linha = uma pessoa executou um serviço numa célula, num mês.

id, obra_servico_id, celula_key, colaborador_id, grupo_id,
mes_ciclo,        -- 'YYYY-MM'
quantidade,       -- parte DESTA pessoa (já rateada)
valor,            -- parte DESTA pessoa (já rateada)
criado_por, criado_em
UNIQUE(obra_servico_id, celula_key, mes_ciclo, colaborador_id)

Regra de ouro do rateio: se uma (celula_key, mes_ciclo) tem mais de uma linha, é execução compartilhada — vale tanto para grupo cadastrado quanto para equipe avulsa. Nesse caso quantidade e valor de cada linha são a fração daquela pessoa, não o total da célula. Para obter o total da célula, some as linhas.

const execucaoCompartilhada = !!linhas[0].grupo_id || linhas.length > 1;
const qtdGravadaTotal = linhas.reduce((acc, l) => acc + (Number(l.quantidade) || 0), 0);

Convenções do esquema

  • mes_ciclo é sempre TEXT no formato 'YYYY-MM'. É a dimensão temporal de quase tudo.
  • Booleanos como INTEGER (1/0) — herança do SQLite. Exceção: financeiro_receitas.com_nota,

que é BOOLEAN de verdade.

  • Enums via CHECK, não tipos ENUM do Postgres. Para aceitar um valor novo é preciso

derrubar e recriar a constraint (há exemplos no database.js).

  • ON DELETE CASCADE nos filhos; SET NULL onde o histórico deve sobreviver

(apagar uma obra não apaga o compromisso da agenda, apenas o desvincula).

Como escrever uma migração

// 1) Coluna nova — sempre checando antes
if (!(await colunaExiste('tabela', 'coluna_nova'))) {
  await pool.query('ALTER TABLE tabela ADD COLUMN coluna_nova TEXT');
  await pool.query('UPDATE tabela SET coluna_nova = ... WHERE ...');  // backfill
}

// 2) Tabela nova
await pool.query(`CREATE TABLE IF NOT EXISTS nova (...);`);

// 3) Operação única e irrepetível
const ja = await db.get('SELECT 1 FROM migracoes_aplicadas WHERE nome = ?', 'minha_migracao');
if (!ja) {
  /* ... executa ... */
  await db.run('INSERT INTO migracoes_aplicadas (nome) VALUES (?)', 'minha_migracao');
}

🔴 Armadilha histórica: constraintContem() compara o nome da constraint, não o conteúdo. Usar isso como verificação derrubou o servidor num loop de process.exit(1). Hoje a checagem correta usa pg_get_constraintdef().

Fluxo de login

POST /api/auth/login { login, senha }
   ↓  bcrypt.compare contra senha_hash
   ↓  jwt.sign({ id, login, perfil, nome }, SECRET, { expiresIn: '12h' })
   ↓
Cliente guarda em localStorage: hs_token, hs_usuario
   ↓
Toda requisição: Authorization: Bearer <token>   (interceptor do axios)
   ↓
Resposta 401 → limpa storage e redireciona para /login

Senha inicial do admin: admin / admin, com precisa_trocar_senha = 1 forçando a troca no primeiro acesso.

Os sete perfis

O perfil ENCARREGADO substituiu o antigo SUPERVISOR (houve migração dos dados). Seu tratamento é especial em três lugares: menu lateral oculto (Layout.jsx), tela inicial redirecionada para /epi (App.jsx → TelaInicial) e Configurações reduzida a "Minha conta".

Duas camadas de autorização

1. permitir(...perfis) — verificação estática, codificada na rota:

router.get('/relatorio', permitir('ADM', 'FINANCEIRO'), handler);
// ADM sempre passa, independentemente da lista

2. permissaoModulo('nome') — verificação dinâmica, consultando perfil_permissoes:

router.use(permissaoModulo('financeiro'));

A segunda é a preferida: permite ao ADM reconfigurar acessos pela tela Controle de Acesso sem alterar código.

10. Domínios funcionais

10.1 Obras e o sistema de células

Geração das chaves — client/src/utils/celulasPredio.js é a fonte da verdade no frontend; server/utils/celulasLabel.js faz o caminho inverso (chave → rótulo) no backend. Os dois precisam concordar.

A lista de células é gerada de cima para baixo, como no desenho:

Cobertura → Caixa d'água → Ático → andares (topo ao térreo) →
Transição → Térreo → Laje Piso Térreo → Fundação → Itens do térreo

Formato das chaves:

Padrão Exemplo Significado
apto-b{bloco}-a{andar}-{pos} apto-b0-a3-2 3º apto do 4º andar, bloco 1
corredor-b{b}-a{a} corredor-b0-a3 Corredor daquele andar
elevador-b{b}-a{a} / escada-b{b}-a{a} Idem
pav-b{b}-a{a} pav-b0-a3 Pavimento inteiro (modo pavimento)
pav-b{b}-a{a}-frente / -fundo Modo frente_fundo
terreo-{i}, terreo-grupo Térreo
fundacao-{n} fundacao-2 Etapa de fundação
cobertura-{item}, terreoitem-{item} Itens livres
caixa_dagua, atico, viga-transicao, pilar-{i} Fixos

Índices de bloco e andar são 0-based; a posição do apartamento também. Mas o número exibido do andar é 1-based e sequencial entre blocos.

Numeração automática dos apartamentos — o multiplicador se adapta à quantidade por andar: até 9 aptos/andar → ×10 (11, 12... 101, 102); 10 a 99 → ×100 (101... 1001). O térreo nunca recebe prefixo. Rótulos podem ser sobrescritos em obra_apto_rotulos.

⚠️ Mudar a geometria da obra depois de ter marcações é perigoso. Remover um andar ou alterar a quantidade de apartamentos muda as chaves geradas, e marcações antigas podem ficar órfãs (apontando para chaves que não existem mais).

10.2 Medição — como o valor é calculado

Esta é a regra mais importante e a que mais gerou defeitos. Três fontes concorrem, nesta ordem de prioridade:

1. Total digitado manualmente  →  vence tudo (valor fechado combinado)
2. Qtd × Unitário da pessoa    →  colaborador_precos (preço específico)
3. Qtd × Unitário do serviço   →  obra_servicos.valor_unitario (padrão)
function calcularTotalPessoa(id) {
  const totalManual = campo(id, 'total');
  if (totalManual !== '') return Number(totalManual) || 0;   // prioridade 1
  return calcularPorQtdUnit(id);                              // prioridades 2 e 3
}

🔴 Defeito histórico (corrigido): ao abrir uma medição para edição, o sistema pré-preenchia o campo Total. Como o total manual tem prioridade, alterar a quantidade mudava a metragem mas não o valor. Hoje a edição preenche qtd e — quando o unitário efetivo difere do padrão — também unit, deixando o total ser recalculado. Há ainda um aviso visual (borda laranja + botão ↻) quando um total fixado diverge de qtd × unit.

Rateio — numa execução compartilhada, o total da célula é dividido igualmente:

const valorTotal = qtdAtual * (servico.valor_unitario || 0);
const valorPorMembro = valorTotal / linhas.length;
const qtdPorMembro = qtdAtual / linhas.length;

Consolidação mensal (/api/medicoes/gerar): agrupa por colaborador todas as células do mês, soma, e inclui também quem só teve diária ou pagamento antecipado. Com filtro de obra ativo, diárias e antecipados só entram se a pessoa também tiver lançamento naquelas obras.

10.3 Recálculo automático

server/utils/recalculoAutomatico.js. Substituiu os antigos botões "Atualizar tudo" e "Recalcular valores", que dependiam de alguém lembrar de clicar.

Dispara quando: muda o preço unitário do serviço, o preço específico de um colaborador, a quantidade de uma célula ou o valor da diária de alguém.

Duas regras invioláveis:

  1. Meses PAGO nunca são alterados — basta um envolvido ter recebido para a célula inteira

ficar protegida.

  1. Execução compartilhada rateia quantidade e valor entre os executores.

Roda em segundo plano (recalcularServicoEmSegundoPlano): não atrasa a resposta ao usuário e qualquer falha vai apenas para o log, sem derrubar a operação principal.

10.4 Diárias, antecipados e desligamento

  • Diárias — quantidade × valor_diaria do cadastro, com rateio opcional por obra

(diaria_obras).

  • Pagamentos antecipados — sete campos de desconto; aceitam valores negativos

(saldo a favor da pessoa).

  • Desligamento — data_desligamento registrada; a pessoa continua aparecendo nos

lançamentos por 35 dias de carência, depois só com o checkbox "incluir desligados". O histórico de medições sempre mostra o nome, mesmo de desligados.

10.5 EPI

Estoque em epi_itens com estoque_minimo. A retirada grava a assinatura do colaborador (base64, capturada em canvas via AssinaturaCanvas.jsx) e gera termo em PDF (utils/termoEpiPdf.js).

Detalhe relevante: epi_retirada_itens copia descrição e CA do item no momento da retirada. Se o catálogo mudar depois, o termo assinado continua refletindo o que foi efetivamente entregue — histórico imutável.

10.6 ASO

Validade de 1 ano "inclusivo": o dia do exame conta como primeiro dia, então o vencimento é data_base + 364 dias (exame em 15/01/2025 vence em 14/01/2026).

A data-base é a última renovação em aso_historico ou, se nunca houve, data_primeiro_aso. Alerta a partir de 6 dias do vencimento. Quem nunca fez ASO aparece primeiro na lista. Apenas CLT (tipo = 'CPF') — PJ é excluído.

10.7 Financeiro — Receitas

Entradas com obra (texto livre, com autocomplete das obras cadastradas), serviço (lista fechada), valor bruto e o flag com_nota. Líquido: com nota desconta 11 %; sem nota, igual ao bruto. A importação por planilha Excel tolera acentos, maiúsculas e espaços ao casar o nome do serviço (normalizarTexto).

Status: EM_ANALISE → CONFIRMADO → PAGO.

10.8 Agenda

Compromissos com período de vários dias (data_fim), horário flexível (HORA, DIA_INTEIRO, MANHA, TARDE, NOITE), destinatários por usuário e/ou por perfil, e lembretes push configuráveis. Quem criou sempre vê o próprio compromisso, mesmo sem se marcar. O ADM tem filtros acumulativos (meus / marcados / internos) e há um quadro com os próximos 20 compromissos.

10.9 Backup

  • Automático: diário, JSON com todas as tabelas listadas em utils/tabelasBackup.js,

mantendo os últimos 7 (auto-YYYY-MM-DD.json). Envio opcional ao Google Drive via conta de serviço.

  • Manual: exportação e importação pela tela de Backup, com cópia de segurança gerada antes

de qualquer importação.

11. Processos em segundo plano

Dois agendadores sobem junto com o servidor (server.js), ambos em memória — não há cron externo nem fila. Se o container reinicia, os temporizadores recomeçam.

Backup automático

Primeira execução 1 minuto após o boot, depois a cada 24 h. Gera o JSON, tenta copiar para a pasta local do Drive (ambiente de desenvolvimento), envia pela API do Drive (produção) e limpa backups com mais de 7 dias.

Agendador de notificações (utils/lembretes.js)

Roda a cada minuto, com primeira verificação 20 s após o boot.

🕐 Fuso horário — ponto crítico. O servidor está em us-east-1. A hora local da máquina não pode ser usada. Todo cálculo é feito explicitamente em UTC−3 (Brasília):

const FUSO_BR = -3;
function agoraBrasilia() {
  return new Date(new Date().getTime() + FUSO_BR * 60 * 60 * 1000);
}

Dois tipos de aviso:

Tipo Quando Para quem
Lembretes da Agenda Conforme minutos_antes de cada compromisso Destinatários do evento
ASO e Experiência Sempre 08:00, uma vez por dia Perfis de alerta do RH

Regras de data dos avisos fixos:

  • Fim de semana recua para sexta (recuarParaDiaUtil): vence sábado ou domingo → avisa sexta.
  • Há também um aviso prévio de 24 h, igualmente ajustado para dia útil.
  • Experiência avisa em dois marcos: 45 e 90 dias (data_admissao + dias − 1).
  • Se o servidor estiver fora do ar às 08:00, o aviso sai assim que voltar, no mesmo dia.

Anti-duplicidade: antes de enviar, grava uma chave única em notificacoes_enviadas. Se a chave já existe, não envia. Para compromissos sem hora exata, usa horário de referência: DIA_INTEIRO/MANHA = 8 h, TARDE = 13 h, NOITE = 18 h.

Limpeza automática: assinaturas push que retornam 404/410 (app desinstalado, permissão revogada) são removidas do banco.

12. Convenções e armadilhas

Idioma do código

Tudo em português: nomes de variáveis, funções, tabelas, colunas e comentários. calcularTotalPessoa, obra_servico_celulas, recalcularServicoEmSegundoPlano. Mantenha o padrão — misturar inglês deixa o código inconsistente.

Comentários explicam o porquê

O código é fortemente comentado, e os comentários registram a razão histórica da decisão — geralmente um defeito real que aconteceu. Exemplo:

// "<> 0" (não apenas "> 0"): um total negativo é um lançamento válido também — acontece
// quando Vale Extra ou Vale Ex RH são lançados com valor negativo (saldo a favor da pessoa).

Não remova esses comentários. Eles são a memória do projeto. Ao corrigir algo não trivial, escreva o porquê no mesmo estilo.

1. Encoding — nunca use Set-Content em arquivos com acentos Corrompe UTF-8 (vira MediÃ§Ã£o). Use sempre a ferramenta de edição do editor. Isto já afetou arquivos do projeto.

2. JSX — comentário logo após && ( quebra o build

{/* ERRADO — derruba o build */}

  {/* comentário aqui */}

4. Deploy "success" não significa aplicação no ar Confirme sempre via API do GitHub, SSH e requisição ao site.

5. Rota nova sem app.use() impede o servidor de subir É proposital (ver verificarRotas.js), mas surpreende quem não conhece.

6. Alterar geometria de obra com marcações existentes gera células órfãs

  2. Leia server/db/database.js — o esquema explica o domínio melhor que qualquer texto.
  3. Leia client/src/utils/celulasPredio.js — entender as células é entender o sistema.
  4. Leia server/utils/recalculoAutomatico.js — concentra as regras financeiras.
  5. Só então abra as telas.

E, acima de tudo: confirme o deploy de verdade antes de dar qualquer tarefa por concluída.
